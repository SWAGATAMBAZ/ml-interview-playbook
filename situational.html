How to answer any situational question

1

Restate and clarify

“So training loss is flat but noisy, and the learning rate is 1e-4 — is this a neural net or a linear model? What batch size?” One or two questions show you don't guess.

2

List hypotheses, most likely first

Group them: data, model/optimisation, evaluation, code/pipeline. Say which you'd check first and why (cheapest check, highest prior).

3

Say how you'd test each

A concrete check per hypothesis: a plot, a tiny experiment, a comparison. “I'd try to overfit one batch” beats “I'd debug it”.

4

Give the fix and the trade-off

What you'd change, what it costs, and how you'd confirm it worked.

5

Prevent it next time

The test, monitor or process that would have caught it. This is what separates senior answers.

⚠️ The reflexes interviewers mark down

Jumping to “retrain the model” or “use a bigger model” before finding the cause · naming one cause and stopping · fixing the symptom without checking data and evaluation first · never mentioning how you'd verify the fix.

A · Training & optimisation (1–10)

1. Your loss is not converging — it keeps wandering up and down — even though the learning rate is already small. Why?

A small learning rate rules out only one cause (overshooting). The usual remaining suspects, in the order I'd check them:

  1. Gradient noise from small or unshuffled batches. With a constant step, SGD never settles; it hovers at a noise floor proportional to learning rate × gradient variance. Fix: larger batch, learning-rate decay, or averaging the weights.
  2. Unscaled features / ill-conditioned loss. One direction is steep and another almost flat, so any single step size is too big for one and too small for the other. Fix: standardise inputs, use Adam or momentum.
  3. Data problems: label noise, outliers, NaNs/infs, wrong labels in some batches — each bad batch kicks the weights.
  4. Bugs: not zeroing gradients, wrong loss sign, applying softmax twice, shuffling features and labels separately, a learning-rate schedule that resets (warm restarts).
  5. A non-stationary or impossible target: features carry no signal, or the loss is non-convex with a noisy plateau.

How I'd diagnose: plot a smoothed loss; try to overfit one tiny batch (if that fails it's a bug); switch to full-batch for a few steps (if it becomes smooth it was noise); check gradient norms and input ranges.

2. Training loss goes down for a while and then suddenly becomes NaN. What do you do?

NaN means a number overflowed or an invalid operation happened. Causes: learning rate too high so weights explode; exploding gradients (deep or recurrent nets); log(0) or division by zero in the loss (probabilities exactly 0/1); invalid inputs (NaN/inf in features, negative values into log or sqrt); mixed-precision overflow.

Steps: find the first step that produced NaN and inspect that batch; assert inputs are finite; lower the learning rate 10×; add gradient clipping; use numerically stable losses (logits + log-sum-exp instead of probability then log; add epsilon/clipping); check normalisation layers and weight initialisation. If it happens only on particular rows, it's a data problem, not an optimiser problem.

3. The loss decreases extremely slowly. How do you speed up convergence?

First decide whether it's slow optimisation or a model that has nothing more to learn (compare with a baseline and with the validation curve).

  • Learning rate too low → run a learning-rate range test and pick the largest stable value; use a schedule with warm-up.
  • Poor conditioning → standardise features, use Adam/momentum, batch normalisation.
  • Saturated activations / vanishing gradients → ReLU-family activations, better initialisation (He/Xavier), residual connections.
  • Too much regularisation (large weight decay, dropout) holding the model back.
  • For boosted trees: learning rate so small that thousands of trees are needed — raise it, tune structure, and lower it again only at the end.
  • Data loader bottleneck — it's wall-clock slow, not optimisation slow; profile it.
4. Training loss is stuck at exactly the same value from the first epoch (e.g. 0.693 for a binary classifier). What does that tell you?

0.693 = ln 2 is the loss of predicting 0.5 for everything: the model is learning nothing. Typical causes: gradients aren't reaching the weights (parameters frozen, optimiser given the wrong parameter list, zero_grad/step in the wrong place, detached tensors); dead ReLUs after a bad initialisation or too-high learning rate; labels shuffled relative to features; all-constant or all-zero inputs after a preprocessing bug; learning rate effectively 0; the target has no relationship to the features.

Check: can it overfit 10 examples? Are gradient norms non-zero? Do weights change between steps? Print a few (x, y) pairs after the full pipeline to confirm they still match.

5. Training loss oscillates wildly from the very start. What's the first thing you change?

Lower the learning rate — oscillation from step one is the classic sign that steps overshoot the minimum (on a quadratic, any step above 2/curvature diverges, and above 1/curvature zig-zags). Then: standardise the inputs so curvature is similar in all directions; increase batch size to reduce gradient noise; add gradient clipping; use warm-up so early large gradients don't throw the weights far away; with Adam, check epsilon and that weight decay is not huge. Confirm by plotting loss against learning rate in a range test: choose a value about 10× below where the loss starts to blow up.

6. Your training loss shows a regular saw-tooth pattern that repeats every epoch. What is happening?

The data aren't shuffled between epochs (or are sorted by class, date or source). Each stretch of the epoch contains a different kind of example, so the model adapts to that chunk, then partly forgets it when the next chunk arrives — the same pattern repeats every pass. Other causes: a cyclical learning-rate schedule, or the last, smaller batch of each epoch having a different loss. Fix: shuffle every epoch (and across shards, not only within a shard), stratify batches if classes are rare, and check the logging isn't mixing per-batch and per-epoch averages.

7. Validation loss is lower than training loss. Is something wrong?

Not necessarily. Innocent explanations: dropout and other regularisers are active in training but switched off at evaluation; training loss is averaged over the epoch while weights were still improving, validation is measured at the end; data augmentation makes training examples harder; the validation set happens to be easier or is small.

Worrying explanations: leakage (duplicates of training rows in validation), a validation set that isn't representative (different period or segment), or a bug such as evaluating on a subset. Check by evaluating the training set in evaluation mode — if that is now lower than validation, it was just the regularisation/averaging effect.

8. You double the batch size and the model gets worse. Why, and what do you adjust?

Larger batches give less noisy gradients and fewer updates per epoch. Two effects follow: the same learning rate now makes less progress per epoch, and the model loses the regularising effect of gradient noise, tending toward sharper minima that generalise slightly worse. Adjust: scale the learning rate up roughly in proportion to batch size (with warm-up), train for more epochs or the same number of updates, and consider a bit more explicit regularisation. Also check batch-norm statistics and that the learning-rate schedule is defined in steps, not epochs.

9. Gradient descent on your linear model takes thousands of iterations, but a colleague's converges in fifty on the same data. What did they probably do?

They standardised the features. With features on very different scales the loss surface is a long narrow valley (large condition number): the learning rate must be small enough for the steepest direction, which makes progress along the flat direction painfully slow, and plain gradient descent zig-zags. After scaling, the contours are close to circular and the gradient points almost straight at the minimum. Other possibilities: they used a second-order or quasi-Newton solver (L-BFGS), momentum/Adam, a better learning rate, or simply the closed-form solution.

10. Two runs with identical code and data give noticeably different results. How do you handle this?

Sources of randomness: weight initialisation, data shuffling, train/validation split, dropout, bootstrap/column sampling in tree ensembles, non-deterministic GPU operations and multi-threading. First, fix seeds everywhere and make the split deterministic to check whether the difference disappears. Then treat the remaining spread as information: report mean ± standard deviation over several seeds, and don't claim an improvement smaller than seed-to-seed variation. If variance is large, the model is unstable — more data, stronger regularisation, more trees, or averaging several seeds (a cheap ensemble) will help. For comparisons, use the same folds and paired tests.

B · Overfitting, underfitting & generalisation (11–20)

11. Training accuracy is 99% and test accuracy is 72%. Walk me through what you do.

That gap is high variance — or leakage/mismatch, so I check those first: is the test set from the same distribution and time period? Any preprocessing fitted on all data? Duplicates across the split?

If it's genuine overfitting, in order of payoff: get more (or augmented) training data; simplify the model (shallower trees, fewer features, higher min_samples_leaf); add regularisation (L1/L2, dropout, lower learning rate with early stopping, subsampling); remove noisy or ID-like features; use bagging/ensembles; tune by cross-validation instead of a single split. I'd plot a learning curve — if validation is still rising with data size, more data is the best investment.

12. Both training and validation error are high. What now?

High bias: the model can't even fit the data it has seen. Options: add informative features or interactions (usually the biggest win); use a more flexible model (linear → gradient boosting); reduce regularisation; train longer / more trees; fix data issues that cap performance (label noise, wrong target definition, features that don't contain the signal). I'd also estimate the best achievable error — human performance or agreement between labellers — because if the problem is inherently noisy, both errors being “high” may already be near the ceiling. More data will not help a high-bias model.

13. You added more training data and performance did not improve. Why?
  • The model is bias-limited: learning curves had already flattened, so it needs more capacity or better features, not more rows.
  • The new data is more of the same — it doesn't cover the cases the model gets wrong.
  • The new data is noisier or from a different distribution (another source, period or labelling standard).
  • You're near the irreducible error for these features.
  • Hyperparameters tuned for the smaller dataset (regularisation, tree depth, number of iterations) are now wrong.

Next step: error analysis to see what kind of examples fail, then collect those (active learning), or add features.

14. Cross-validation says 90%, the held-out test set says 80%. How do you explain the gap?

Something made the CV estimate optimistic or the test set different:

  • Leakage inside CV: scaling, imputation, feature selection, target encoding or oversampling done before splitting.
  • Wrong split type: random folds on grouped or time-ordered data, so near-duplicates sit on both sides.
  • Tuning optimism: the reported CV score is the best of many configurations.
  • Distribution shift: the test set is from a later period or different population.
  • Small test set: the difference is within sampling error — compute a confidence interval.

I'd rebuild everything inside a pipeline, use group/time-aware splits, and run nested CV to get an honest number.

15. Your model does well on the test set but poorly on new data collected next month. Why?

The test set shared something with training that next month's data doesn't: the same time period (so no temporal drift), the same customers/devices, the same data pipeline. Causes: concept or data drift, seasonality the training window never saw, a feature that was only available retrospectively (leakage), or training–serving skew in how features are computed live. Fix the evaluation first — hold out the most recent period and unseen entities so the offline number predicts the future — then add drift monitoring, retrain on a recent window, and prefer features that are stable over time.

16. A very deep decision tree gets 100% training accuracy. Your manager is pleased. What do you say?

That 100% on training data mostly proves the tree has memorised it: an unrestricted tree keeps splitting until every leaf is pure, including noise and mislabelled rows. The only number that matters is performance on data it hasn't seen. I'd show the cross-validated score, then control complexity — max_depth, min_samples_leaf, cost-complexity pruning chosen by CV — or move to a random forest or gradient boosting, which keep the flexibility while averaging away the variance. I'd also check for an ID-like or leaky feature that makes perfect separation suspiciously easy.

17. Regularisation made your model worse. How is that possible?

Regularisation trades variance for bias; it only helps when variance was the problem. If the model was already underfitting, or the penalty is too strong, you add bias and lose accuracy. Other causes: features weren't standardised, so the penalty hits coefficients unevenly; the intercept was penalised; the regularisation strength wasn't tuned by cross-validation; with Lasso, a group of correlated useful features was collapsed to one arbitrary survivor. Check the train vs validation error before and after: if both rose, it's too much bias — reduce the penalty.

18. You have only 500 labelled rows and 2,000 features. How do you build a model that generalises?

p ≫ n is a recipe for overfitting, so everything is about reducing variance and getting an honest estimate:

  • Simple, strongly regularised models: Lasso / Elastic Net logistic regression, linear SVM, or a small random forest.
  • Reduce dimensionality with domain knowledge, univariate filters, or PCA — inside the CV loop.
  • Repeated stratified or nested cross-validation; report a confidence interval.
  • Transfer learning or pretrained embeddings if the data are text/images.
  • Get more labels where the model is uncertain (active learning), or use semi-supervised methods.

And never select features on the full dataset before cross-validating — that alone can turn pure noise into “90% accuracy”.

19. Your model's error is fine on average but terrible for one customer segment. What do you do?

Averages hide slices. First measure: per-segment metrics with confidence intervals and sample sizes. Then find the cause: the segment is under-represented in training; it behaves differently (a different relationship between features and target); its data quality is worse (more missing values, different source system); or its labels are noisier.

Remedies: collect or up-weight data for that segment; add features that describe it or interaction terms; train a segment-specific model or let a tree model split on the segment; set segment-specific thresholds; if it can't be fixed quickly, route that segment to a fallback rule or human review. Add the slice to the standing evaluation so it can't regress silently.

20. How do you decide between collecting more data and building a more complex model?

Plot a learning curve (score against training-set size). If training and validation scores have converged at an unsatisfactory level, the model is bias-limited — more data won't help; add features or capacity. If there's a large gap and the validation curve is still rising, it's variance-limited — more data (or regularisation) will help, and you can extrapolate roughly how much. Then weigh costs: labelling cost and time versus engineering and serving cost of a bigger model. Error analysis decides which data: more examples of the failing cases beat more random rows.

C · Data problems (21–30)

21. 40% of the values in an important feature are missing. What do you do?

Don't drop it reflexively. First ask why it's missing: at random, dependent on other columns, or dependent on its own value (e.g. income withheld by high earners)? Often the missingness itself is predictive.

  • Add a missing-indicator column, then impute (median for a skewed numeric, a “Missing” category for a categorical).
  • Try model-based imputation (KNN / iterative) if other columns predict it well.
  • Use a model that handles NaN natively (XGBoost, LightGBM, HistGradientBoosting).
  • Check whether it will also be missing at prediction time, at the same rate.

Fit the imputer on training folds only, and compare options by cross-validation instead of guessing.

22. One feature gives your model 0.99 AUC. What's your reaction?

Suspicion before celebration: it's probably target leakage. I'd ask how and when that feature is recorded. Typical culprits: a field updated after the outcome (“account_closed_date” for churn, “chargeback_flag” for fraud), a proxy created from the label, an ID or timestamp that encodes how the data was collected, or post-treatment information. Tests: is the feature available at the moment of prediction in production? Does performance survive a strict point-in-time rebuild of the training set? If it's leakage, remove it; if it's genuinely available in advance, great — but then the problem may not need ML at all, just that rule.

23. You suspect that many training labels are wrong. How do you proceed?
  • Measure it: re-label a random sample (ideally by two people) to estimate the noise rate and whether errors are random or systematic.
  • Find the bad ones: rows where a cross-validated model is confidently wrong are prime suspects (confident learning); review those first.
  • Be robust: prefer bagging/random forests over AdaBoost-style methods that keep up-weighting the “hard” (mislabelled) points; use stronger regularisation, early stopping, label smoothing or robust losses.
  • Protect evaluation: clean the validation/test labels carefully — noisy test labels cap and distort every metric.
  • Fix the source: clearer labelling guidelines, multiple annotators with adjudication.

Random noise mostly costs accuracy; systematic noise teaches the model the wrong rule and is far more harmful.

24. A categorical feature has 50,000 distinct values. How do you use it?

One-hot is impractical (huge, sparse, most levels with a handful of rows). Options: frequency encoding; target (mean) encoding with smoothing and out-of-fold computation so a row's own label never enters its feature; hashing into a fixed number of buckets; grouping rare levels into “Other”; learned embeddings in a neural model; or native handling in CatBoost/LightGBM. Also consider replacing the ID with attributes of the entity (merchant category, age, volume), which generalise to unseen values. Plan for categories never seen in training, and check that the model isn't just memorising IDs — validate on unseen entities if that's how it will be used.

25. In production you receive a category value the model never saw in training. What happens, and how should you design for it?

Depending on the encoder: an exception (the service fails), an all-zeros one-hot row (treated like the baseline category), or an arbitrary code — all bad if unplanned. Design: OneHotEncoder(handle_unknown="ignore") or an explicit “unknown/rare” bucket that the model has seen during training (map infrequent training levels to it so it has learned a sensible effect); target encoders fall back to the global mean; hashing never fails. Log the rate of unknown values as a data-quality metric — a spike means an upstream change or drift and may signal that retraining is due.

26. Your dataset has duplicate rows. Does it matter?

Yes, in two ways. If duplicates (or near-duplicates such as the same customer on different days) land on both sides of the train/test split, the model is partly tested on data it memorised and the score is inflated. And within training, duplicates silently up-weight those examples and make standard errors look smaller than they are. First find out why they exist: a join that fanned out, repeated logging, or genuine repeated events. Remove true duplicates before splitting; for repeated entities use group-aware splits; if repetition reflects real frequency, keep it but make sure the split is by group.

27. You're given data from two sources that measure the same thing differently. How do you combine them?

Profile each source separately: units, definitions, time zones, coding of categories, missing-value conventions, collection period and population. Harmonise units and definitions explicitly; map categories to a shared scheme; keep a source column so the model can absorb remaining differences and so you can evaluate per source. Check the label means the same thing in both. Validate by training on one source and testing on the other — a large drop reveals systematic differences. If one source will be the only one in production, weight or fine-tune toward it, and make sure the evaluation set reflects that mix.

28. How do you find and deal with outliers before modelling?

Look first (histograms, box plots, scatter plots), then use rules: IQR fences, robust z-scores based on median/MAD, or Isolation Forest for multivariate oddities. The key step is deciding what each outlier is: a data error (fix or remove), a rare but real value (keep — it may be the most valuable row), or the very thing you're trying to detect (fraud).

Treatment depends on the model: linear models and K-means are sensitive, so cap/winsorise, log-transform or use robust losses (Huber); tree models are largely insensitive to outliers in features but not in a regression target. Whatever thresholds you learn must come from training data only.

29. The numeric target is heavily right-skewed (most values small, a few huge). How does that change your approach?

Squared-error training will be dominated by the few huge values. Options: model log(1 + y) and transform back (remember the back-transformed mean is biased low — correct it or accept you're predicting something closer to the median); use a loss suited to the data (Poisson, Gamma or Tweedie for counts/amounts; MAE or Huber for robustness; quantile loss if a percentile matters); cap extreme values if they're errors. Choose the metric to match the business: RMSE punishes big misses, MAE treats all rupees equally, RMSLE measures relative error. Evaluate separately on the tail, since that's often where the money is.

30. You have a huge pool of unlabelled data and budget to label only 1,000 examples. How do you choose them?

Start with a random sample of a few hundred — you need an unbiased set for evaluation and a first model. Spend the rest with active learning: train, then label the examples the model is least certain about (probabilities near the threshold, or disagreement among an ensemble), mixed with diversity sampling (pick from different clusters) so you don't label 500 near-identical edge cases. Repeat in rounds. Stretch the labels further with pretrained embeddings/transfer learning, weak supervision (heuristic labelling rules) and semi-supervised pseudo-labelling. Keep the evaluation set random and untouched by the selection process, or your metrics will be biased.

D · Imbalance, metrics & thresholds (31–40)

31. Your fraud model has 99.5% accuracy but the business says it's useless. Explain.

If only 0.5% of transactions are fraud, predicting “not fraud” for everything scores 99.5% accuracy while catching nothing. Accuracy is dominated by the majority class. Look at the confusion matrix and at recall (share of fraud caught), precision (share of alerts that are real), PR-AUC, and the money: fraud value prevented versus cost of false alarms. Then fix the model's behaviour: class weights or resampling in training, and — most importantly — a decision threshold chosen for the business trade-off or the review team's capacity rather than the default 0.5.

32. Precision is high but recall is very low. How do you raise recall, and what will it cost?

The quickest lever is the threshold: lower it and recall rises while precision falls — plot the precision–recall curve and pick the point the business can live with. To move the whole curve outward rather than slide along it: class weights or resampling so the model pays more attention to positives; features that describe the missed positives (do error analysis on the false negatives — are they a distinct sub-type?); more positive examples; a stronger model. The cost is more false positives, so quantify it: “recall goes from 40% to 70%, alerts per day triple, precision drops from 90% to 55%”.

33. ROC-AUC is 0.95, yet at any usable threshold precision is under 10%. How can both be true?

ROC-AUC measures ranking using the false-positive rate, whose denominator is all negatives. With 1 positive per 1,000 rows, a 1% false-positive rate still means about 10 false alarms for every real positive — precision around 9% even with excellent ranking. Nothing is broken; the metric just hides the base rate. Report PR-AUC and precision at the operating recall (or precision@k) instead, compare against the base rate, and judge the model on whether the top-scored cases are worth acting on.

34. How do you choose the classification threshold for a model that will go live?

From costs or constraints, not by default. If you can price the errors, and probabilities are calibrated, predict positive when p > C_FP / (C_FP + C_FN). If there's a capacity limit (the team can review 200 cases a day), take the top 200 scores — that fixes the threshold. If there's a requirement (“recall must be ≥ 90%”), take the threshold that meets it with the best precision. Otherwise maximise F1 or Fβ. Choose it on a validation set, confirm on a separate test set, and revisit it whenever the class balance or the model changes — a threshold is tied to a specific score distribution.

35. You applied SMOTE and cross-validation scores jumped, but production performance is poor. What went wrong?

Almost certainly SMOTE was applied before the split. Synthetic points are interpolations of real minority points, so validation folds contained near-copies of training rows — leakage — and the validation set no longer had the real class balance. Resampling must happen inside each training fold only (an imbalanced-learn Pipeline), and validation/test must keep the natural distribution. Also remember that after resampling the predicted probabilities are inflated, so thresholds chosen on balanced data don't transfer; recalibrate or tune the threshold on untouched data. Often class weights plus threshold tuning do as well with less risk.

36. After you used class weights, the model's predicted probabilities look far too high. Why, and does it matter?

Weighting (or over/under-sampling) tells the model positives are more common than they are, so its scores are no longer estimates of the true probability — a “0.6” may correspond to a real rate of 5%. It doesn't matter if you only need ranking or a tuned threshold. It matters a lot if the number is used as a probability: expected-loss calculations, pricing, risk reports. Fix by recalibrating on a held-out set with the natural class balance (Platt/isotonic), or correct the prior analytically, or train without weights and handle imbalance through the threshold alone.

37. For a cancer-screening model, which metric do you optimise? And for a spam filter?

Screening: a missed cancer (false negative) is far worse than an unnecessary follow-up test, so prioritise recall/sensitivity — e.g. maximise specificity subject to sensitivity ≥ 95–99% — because positives go on to a confirmatory test. Spam: sending a real email to spam (false positive) is worse than letting one spam through, so prioritise precision, with recall as the secondary goal. In both cases I'd say the metric follows from the asymmetric cost of errors and from what happens next in the workflow, and I'd report the full confusion matrix at the chosen operating point.

38. Model A has higher AUC, model B has higher F1. Which do you ship?

They answer different questions: AUC measures ranking over all thresholds; F1 measures one operating point (and depends on the threshold each model happened to use). So first compare fairly — tune each model's threshold on validation data for the metric that reflects the real decision. If the product uses a fixed decision (alert / don't alert), compare precision and recall at the operating point that matters. If it uses the ranking (top-k recommendations, prioritised queues), AUC or precision@k matters more. Then check stability across folds, calibration, latency and cost. Small differences inside the noise → ship the simpler one.

39. Your regression model has R² = 0.9 but the users say the predictions are useless. Why might that be?
  • R² is relative to predicting the mean; if the target varies hugely, 0.9 can still leave errors too large for the decision. Report MAE in real units.
  • The users care about a range where the model is weak (small values, the tail, a specific segment).
  • R² was measured in-sample or with leakage (e.g. a lagged target that isn't available at prediction time).
  • The model is biased in a systematic way — good correlation, wrong level.
  • Predictions arrive too late or aren't actionable.

I'd ask what accuracy they need, in their units, for which decisions, and evaluate against that.

40. The test set has only 200 rows. How confident are you in a reported accuracy of 85%?

Not very. The standard error is √(0.85 × 0.15 / 200) ≈ 2.5 points, so a 95% interval is roughly 80–90%. A “2-point improvement” between models on this set is noise. With a rare positive class it's worse — recall might rest on a dozen examples. What I'd do: report confidence intervals (bootstrap the test set for metrics like AUC or F1); use repeated or nested cross-validation to use all the data; compare models with paired tests on the same examples (McNemar); and collect a larger test set if the decision is important.

E · Features & model choice (41–50)

41. Two features are 0.97 correlated. Do you remove one?

It depends on the goal. For prediction with trees or regularised models, it rarely hurts accuracy; keeping both is fine. For interpretation it's a problem: in a linear model the coefficients become unstable with large standard errors and can flip sign, and tree importances/SHAP split credit arbitrarily between the two. Then I'd drop one (keep the cheaper, more reliable or more interpretable), combine them (average, ratio, PCA component), or use Ridge. Check with VIF, and confirm by cross-validation that removing one doesn't cost accuracy. Fewer redundant features also means less to maintain and monitor.

42. You have 5,000 candidate features. How do you narrow them down?
  1. Cheap filters: drop constants, near-constants, duplicates, columns that are mostly missing, and anything unavailable at prediction time or leaky.
  2. Redundancy: cluster highly correlated features and keep one per cluster.
  3. Relevance: univariate screens (mutual information) as a rough cut.
  4. Model-based: L1-regularised model or gradient boosting, then permutation importance or SHAP on validation data; recursive elimination if affordable.
  5. Stability: keep features selected consistently across folds/bootstraps.

All selection happens inside cross-validation. I'd stop when dropping more starts to cost validation performance, and favour features that are cheap, stable and explainable.

43. Feature importance ranks a random-ID column near the top. What does that mean?

Either the importance method is misleading or the ID leaks. Impurity-based importance from trees favours high-cardinality columns: an ID offers thousands of split points, so by chance some reduce impurity on the training data. Permutation importance on a held-out set will show its real value (near zero). If it's still important on held-out data, the ID carries information — e.g. IDs assigned in time order, or in blocks by region or by outcome — which is leakage or a proxy. Either way remove it, and prefer permutation importance or SHAP on validation data for decisions.

44. A simple logistic regression scores 0.84 AUC and a tuned XGBoost scores 0.85. Which do you deploy?

Probably the logistic regression. A 0.01 gap is often inside cross-validation noise (check fold-by-fold results), and the linear model is cheaper to serve, faster, easier to explain to regulators and stakeholders, easier to debug and monitor, and more stable under drift. I'd deploy XGBoost only if the gain is statistically solid and worth real money at the operating point, and the latency/maintenance budget allows. The small gap also tells me the remaining signal isn't in non-linearities — better features or data are likely the next lever for either model.

45. The regulator requires every loan decision to be explainable. How does that change your modelling?

I'd start from inherently interpretable models: logistic regression on sensibly binned features (a scorecard), a GAM, or a shallow tree; if a boosted model is needed, add monotonic constraints (risk can't fall as debt rises) and limit interactions. Each decision needs reason codes — the top factors that pushed the score down — from coefficients or SHAP. I'd exclude protected attributes, test for proxies and measure outcomes across groups, document data, assumptions and limitations in a model card, check stability over time, and keep full versioning for audits. Accuracy is traded for transparency deliberately, and I'd quantify what that trade costs.

46. Predictions must be returned in under 10 ms. What do you change?

Work out where the time goes — usually feature retrieval, not the model. Then: precompute features and store them in a low-latency key-value store; drop features that need slow lookups; choose a light model (linear, small gradient-boosted model with limited trees/depth) or distil a large model into a small one; compile/export to an optimised runtime (ONNX Runtime, Treelite); keep the model in memory, avoid Python overhead on the hot path; cache results for repeated requests; use a two-stage design (cheap filter, expensive model only for the uncertain few). Set a timeout with a sensible fallback, and measure p99 latency, not the average.

47. When would you choose a linear model over gradient boosting, and when the reverse?

Linear: small data; very high-dimensional sparse features (text); need for clear explanation and calibrated probabilities; strict latency; the relationship is roughly additive; you need to extrapolate beyond the training range; you want a stable baseline.

Boosting: medium/large tabular data with non-linear effects, thresholds and interactions; mixed feature types and missing values; accuracy is the priority and you have time to tune and monitor.

In practice I build the linear baseline first; the size of the gap between it and boosting tells me how much non-linearity matters and whether the extra complexity is justified.

48. Your manager asks, “Why not just use deep learning?” for a tabular churn problem. What do you answer?

For tabular data of ordinary size, gradient-boosted trees usually match or beat neural networks, with far less tuning, training cost and data. Tabular features are a mix of scales and types with sharp thresholds and many irrelevant columns — the kind of structure trees handle naturally and networks don't. Deep learning earns its place with images, text, audio, sequences, very large datasets, or when you need learned embeddings for huge-cardinality IDs or to combine modalities. I'd offer to benchmark both against a baseline, but set expectations: the gains here are more likely from better features and labels than from a bigger model.

49. A rule-based system is already in production. How do you decide whether ML is worth it?

Treat the rules as the baseline. Measure them on a labelled sample: precision, recall, cost of errors, and how much effort they take to maintain. Estimate the upside: how much better could a model plausibly be (a quick prototype on historical data), and what is one point of improvement worth? Weigh that against the costs ML adds — labels, pipelines, monitoring, retraining, explainability. ML is worth it when patterns are too complex or fast-changing for rules, there's enough labelled data, and errors are tolerable. Often the best design is hybrid: rules as guardrails and features, the model for ranking, and an A/B test to prove the gain.

50. A stakeholder wants one more feature added the day before launch. What do you check?
  • Availability at prediction time: does it exist, at that moment, in production, with the same definition as in training?
  • Leakage: is it recorded after the outcome?
  • Quality and coverage: missing rate, history length, stability over time, who owns the pipeline.
  • Value: does it improve cross-validated performance beyond noise, especially on the slices that matter?
  • Risk: fairness/legal issues, extra latency, a new dependency to monitor.

A day before launch I'd almost always ship without it and add it in the next iteration behind an A/B test — a late, unvalidated feature is a classic source of incidents.

F · Model-specific situations (51–60)

51. In your linear regression, a coefficient has the opposite sign to what everyone expects. What's going on?

Most often multicollinearity: the feature is strongly correlated with another one, and the two coefficients are jointly unstable — one goes up, the other goes down to compensate. Check VIFs and the correlation matrix; refit without the partner feature and see whether the sign flips back. Other causes: an omitted confounder (Simpson's paradox — the sign is right “holding other things fixed” but wrong marginally); the coefficient isn't statistically different from zero (look at its confidence interval); outliers or high-leverage points; a data/encoding error; or the expectation is simply wrong. A coefficient always means “effect with the other features held constant”, which is not the same as the raw relationship.

52. Your residual plot shows a funnel shape (errors grow with the prediction). What does it mean and what do you do?

Heteroscedasticity: the error variance isn't constant. Coefficients are still unbiased, but standard errors, p-values and confidence/prediction intervals are wrong, and the fit pays too much attention to the high-variance region. Confirm with a Breusch–Pagan or White test. Fixes: transform the target (log or Box–Cox — common for prices, incomes, counts); weighted least squares with weights ∝ 1/variance; heteroscedasticity-robust (HC3) standard errors if you only need valid inference; or model the right distribution directly (Poisson/Gamma GLM). If you need prediction intervals, use quantile regression so the interval width can vary.

53. Logistic regression prints a convergence warning and the coefficients are enormous. Why?

Probably (quasi-)perfect separation: some feature or combination predicts the class perfectly, so the likelihood keeps improving as the weights grow without limit and the optimiser never converges. That feature may be leakage, or a rare category that appears in only one class. Other causes: unscaled features making the optimisation ill-conditioned; too few iterations; strong collinearity. Fixes: standardise the inputs; keep (or increase) L2 regularisation — lower C; raise max_iter; remove or investigate the separating feature; merge rare categories. If you need unbiased inference with separation, use Firth's penalised likelihood.

54. Your random forest is very accurate but too slow and too large to deploy. What are your options?

Size and latency grow with number of trees × depth. Options: fewer trees (accuracy usually plateaus early — check the OOB curve); limit depth or raise min_samples_leaf so trees are smaller; cut features; train on a subsample (max_samples). Or switch models: gradient boosting typically reaches the same accuracy with far fewer, shallower trees; distil the forest into a small boosted model or linear model. Engineering: compile trees (Treelite/ONNX), use float32, batch predictions, or precompute scores in batch if real-time isn't truly required. Measure the accuracy–latency trade-off at each step.

55. Your gradient-boosting model: training loss keeps falling, validation loss starts rising after 300 trees. What do you do?

That's overfitting in the number of rounds — each extra tree is now fitting noise. Use early stopping: keep the model at the best validation iteration (≈300). Then improve the trade-off: lower the learning rate and let early stopping find the new tree count; make trees weaker (smaller max_depth/num_leaves, larger min_child_weight/min_child_samples); add row and column subsampling; raise L2/γ. Make sure the early-stopping set is separate from the final test set, and when retraining on all data use the tree count found (scaled up slightly for the larger dataset).

56. XGBoost with default settings performs worse than a random forest on your data. Why could that be?
  • Small or noisy dataset: boosting chases noise; averaging (RF) is more robust.
  • Not tuned: boosting is much more sensitive — the default 100 trees at learning rate 0.3 with depth 6 may over- or underfit. Tune learning rate with early stopping, depth, min_child_weight, subsampling, regularisation.
  • No early stopping or an unsuitable evaluation metric.
  • Label noise or outliers in the target.
  • Categoricals encoded poorly (arbitrary integer codes).

A random forest is hard to get badly wrong; boosting usually wins only after tuning. If the tuned gap stays negative, accept the forest.

57. A kNN classifier worked well in your prototype with 5 features and collapsed when you added 200 more. Why?

The curse of dimensionality. In high dimensions distances concentrate — the nearest and farthest neighbours are almost equally far — so “nearest” stops meaning “similar”. Worse, most of the 200 new features are probably irrelevant, and every one contributes equally to the distance, drowning the five that matter. Also check they were scaled. Fixes: feature selection; dimensionality reduction (PCA or learned embeddings) before kNN; a metric that weights features (metric learning); or switch to a model that ignores irrelevant features by itself, such as gradient boosting or a regularised linear model.

58. Your SVM takes hours to train on 2 million rows. What do you do?

Kernel SVM training scales between quadratic and cubic in the number of rows, so it's the wrong tool at this size. Options: a linear SVM solver (LinearSVC or SGDClassifier(loss="hinge")), which scales linearly; if non-linearity is needed, approximate the kernel with random Fourier features or Nyström and train a linear model on top; train on a well-chosen subsample; or change model family — gradient boosting for tabular data. Also confirm features are scaled (unscaled data slows the solver dramatically) and that C and γ aren't at extremes producing a huge number of support vectors.

59. K-means gives different clusters every time you run it. Is that a problem?

K-means only finds a local optimum that depends on the starting centroids, so some variation is expected. Reduce it with k-means++ initialisation, many restarts (n_init) keeping the lowest inertia, and a fixed seed for reproducibility. But large instability is a message: the data may not have K well-separated, roughly spherical clusters. Check by measuring agreement between runs (adjusted Rand index) and silhouette scores; try other values of K; scale features and remove outliers; consider a model that fits the shape better (GMM, HDBSCAN). If no K gives stable clusters, say so — the structure may be a continuum rather than groups.

60. Naive Bayes outputs probabilities that are almost always 0.00 or 1.00. Should you trust them?

No. Naive Bayes multiplies the evidence from each feature as if they were independent. Real features are correlated (in text, “credit” and “card” travel together), so the same evidence is counted several times and the posterior is pushed to the extremes. The ranking and the predicted class are often still good; the probability values are not. If you need real probabilities, calibrate on held-out data (isotonic or sigmoid via CalibratedClassifierCV) or use logistic regression. Also check smoothing: with α too small, a rare word can swing the result on its own.

G · Validation & experiments (61–70)

61. Your dataset has many rows per customer. How should you split it, and what happens if you split randomly?

Split by customer (GroupKFold / a group-wise holdout) so all rows from one customer are on the same side. With a random split, the model sees other rows from the same customer in training and can recognise the customer rather than learn general patterns; the validation score then measures memorisation and overstates performance on new customers — sometimes dramatically. The rule: the split should mimic how the model will be used. If it will score new customers, hold out customers; if it will score existing customers in future months, hold out by time; often you need both.

62. You tried 200 hyperparameter combinations and report the best cross-validation score. Is that number trustworthy?

It's optimistically biased: the maximum of 200 noisy estimates is partly luck (the “winner's curse”), more so with small data. The honest performance estimate comes from data not used in the selection: a final untouched test set, or nested cross-validation where the search is repeated inside each outer fold. Also look at whether the top configurations are within one standard error of each other — if so, prefer the simplest. And don't go back and re-tune after looking at the test set, or it stops being a test set.

63. Offline, the new model beats the old one by 3%. In the A/B test there's no difference. Give possible reasons.
  • The offline metric isn't the business metric (better AUC ≠ more conversions).
  • Offline evaluation was optimistic: leakage, a split that doesn't mirror production, old data.
  • Training–serving skew: features differ online.
  • Offline data were generated under the old model's decisions (selection/feedback bias), so they can't show what the new model would do.
  • The improvement is in cases that don't change any decision.
  • The new model is slower and the latency cancels the gain.
  • The test is underpowered or too short; novelty effects.

I'd check implementation parity first (same inputs → same outputs offline and online), then power, then whether the offline metric correlates with the online one historically.

64. The A/B test shows p = 0.04 after three days and the PM wants to ship. What do you say?

Not yet, if the planned duration was longer. Checking repeatedly and stopping the first time p < 0.05 inflates the false-positive rate well beyond 5%. Three days also misses weekly seasonality and may be a novelty effect. I'd ask: was the sample size fixed in advance and has it been reached? Is the split healthy (no sample-ratio mismatch)? What do the confidence interval and guardrail metrics say? If we need early decisions, use a sequential testing method designed for it. If the planned sample is reached and the effect is practically meaningful with guardrails intact, ship.

65. An A/B test result is “not statistically significant”. Does that mean the change has no effect?

No — it means the data are consistent with no effect, not that they prove it. Look at the confidence interval: if it's narrow around zero (say −0.2% to +0.3%), you can conclude any effect is too small to matter. If it's wide (−2% to +6%), the test was underpowered and is inconclusive; a worthwhile effect may well exist. Check the power calculation: was the sample large enough for the minimum effect we care about? Options: run longer, reduce variance (CUPED, better metric), or make a bolder change. Don't slice into segments until something is “significant” — that's p-hacking.

66. You can't run an A/B test (legal or practical reasons). How do you estimate the impact of the model?

Use quasi-experimental methods, each with assumptions to defend: difference-in-differences (compare the change in a treated group with a similar untreated group; needs parallel trends); staggered or geographic roll-out used as a natural experiment; synthetic control (build a weighted mix of untreated units that matched the treated one before launch); regression discontinuity if treatment depends on a score threshold; propensity matching/weighting to balance observed confounders; interrupted time series with a forecast of what would have happened. I'd run placebo checks, state the assumptions plainly, and present the result as a range, not a point.

67. You're asked to validate a forecasting model. A colleague used 5-fold cross-validation with shuffling. What's wrong?

Shuffling puts future observations in the training folds and past ones in validation, so the model “predicts” days whose neighbours it has already seen — and with lag features, it may literally have the answer. The score is far too optimistic. Use rolling-origin evaluation: train on data up to time t, forecast the next horizon, move forward, repeat. Match the horizon and retraining frequency to production, leave a gap equal to any feature look-ahead or label delay, compare with naive and seasonal-naive baselines, and report error by horizon.

68. The treatment group in your experiment has 50.9% of users instead of the planned 50%. Do you care?

With large samples, yes. Run a chi-square test on the counts: at a million users, 50.9/49.1 is wildly unlikely by chance — a sample ratio mismatch. It means assignment or logging is broken in a way that probably differs between groups (redirects losing users, bots filtered unequally, a crash in one variant, a tracking bug), so the two groups are no longer comparable and the results can't be trusted, whatever the p-value on the main metric. Stop interpreting, find the cause (break down by browser, platform, date), fix it and rerun.

69. You tested 20 metrics and one is significant at p = 0.03. How do you report it?

With 20 independent tests at α = 0.05 you expect one false positive by chance, and the probability of at least one is about 64%. So a single p = 0.03 among 20 is weak evidence. Ideally a primary metric was declared in advance; everything else is exploratory. Apply a correction — Bonferroni (0.05/20 = 0.0025) to control the chance of any false positive, or Benjamini–Hochberg to control the false-discovery rate. I'd report it as a hypothesis worth a follow-up test, not as a finding, and show all 20 results rather than only the “winner”.

70. How do you make sure your offline evaluation will predict real-world performance?
  • Split like production: hold out the most recent period and unseen entities.
  • Features as of prediction time: point-in-time correct joins, no late-arriving fields.
  • Same pipeline for training, evaluation and serving.
  • Metric tied to the decision: the operating threshold or top-k that will be used, weighted by business value.
  • Representative population: include the cases the current system rejects, or acknowledge the selection bias.
  • Slices and uncertainty: report segments and confidence intervals.
  • Close the loop: shadow deployment, then compare offline predictions with online outcomes and track how well offline gains have translated historically.

H · Production & MLOps (71–82)

71. Model accuracy dropped ten points overnight. What's your investigation plan?

A sudden drop is almost always a pipeline problem, not the world changing overnight.

  1. Is the alert real? Metric code, label delay, sample size.
  2. What changed yesterday? Deployments (model, feature code, upstream services), schema changes, config.
  3. Data quality: null rates, new categories, unit or encoding changes, a join returning fewer rows, a stale feature table, default values being served.
  4. Drift per feature and the prediction distribution — which inputs moved?
  5. Which slice? If one region/platform accounts for the drop, the cause is local.

Mitigate first (roll back or switch to the fallback), fix the root cause, then add the missing test or monitor. I wouldn't retrain until I knew why — retraining on broken data bakes the bug in.

72. Performance has been sliding slowly over six months. How is that different from a sudden drop?

Gradual decay points to drift: the population of inputs is shifting (data drift) or the relationship between inputs and outcome is changing (concept drift) — customer behaviour, competitors, prices, fraud tactics. Confirm by comparing feature distributions and performance by month, and by backtesting how accuracy falls with model age. The response is a retraining policy rather than a hotfix: retrain on a recent window, at a cadence matched to the measured decay, with validation gates; consider recency weighting; add features that are more stable; and set alerts on drift and performance so the next slide is caught in weeks, not months.

73. The model was excellent in the notebook but is poor once deployed. What are the usual reasons?
  • Training–serving skew: features computed by different code or from different sources online; different default for missing values; different time zone or units.
  • Leakage in training: features that used information not available at prediction time.
  • Stale or late features online (yesterday's aggregate instead of real-time).
  • Population mismatch: trained on a filtered or historical population.
  • Preprocessing not shipped with the model (scaler, encoder, vocabulary versions).
  • Library/version differences.

Diagnose by logging production feature vectors and predictions, replaying them through the offline pipeline, and diffing row by row. Prevent with a single feature definition (feature store), the preprocessing packaged inside the model artefact, and a shadow deployment before launch.

74. True labels arrive two months after the prediction. How do you monitor the model meanwhile?

Use leading indicators: data-quality checks (schema, nulls, ranges, volumes); drift in input features (PSI, KS) against a reference window; drift in the distribution of predictions and of the share above threshold; proxy outcomes available sooner (early delinquency instead of default, clicks instead of purchases); and human review of a small random sample to get quick labels. Performance can also be estimated from calibrated confidence. When labels do arrive, join them back, compute the real metrics and check how well the early signals predicted them — that tells you which alerts deserve trust.

75. Your drift monitor fires an alert on three features. Do you retrain?

Not automatically. First check it's real and not a data bug (a unit change looks like drift, and retraining on it would be wrong). Then ask whether it matters: are these features important to the model? Has the prediction distribution or any performance proxy moved? With very large samples, statistical tests flag trivial shifts, so judge by effect size. If inputs shifted in an important way and performance is at risk, retrain on recent data and validate against the current model on the newest labelled period before promoting. If it's seasonal and expected, widen the reference window instead of retraining every time.

76. You retrained the model on fresh data and it's worse than the one in production. What do you do?

Don't promote it — that's exactly what a validation gate is for. Then find out why: the new data may contain a pipeline bug, label errors or labels that aren't mature yet (recent rows with incomplete outcomes); the training window may now exclude a useful period or include an abnormal one (a promotion, an outage); hyperparameters tuned for the old data may not fit; the evaluation set may favour the old model (it was tuned on it); or it's just run-to-run variance. Compare both models on the same recent holdout with confidence intervals and by slice, and keep the champion until a challenger clearly wins.

77. An upstream team changed a field from rupees to thousands of rupees without telling you. How would you have caught it?

With data validation at the boundary: schema and range checks on every batch or request (expected type, min/max, mean within tolerance of the reference), and distribution monitoring — a 1000× shift in the mean lights up PSI immediately. Plus data contracts with upstream owners so changes are announced and versioned, alerts on the prediction distribution (the model's outputs would shift too), and a canary/shadow stage for upstream changes. In the service itself, fail safe: when an input is out of range, flag it and fall back rather than produce a confident nonsense prediction.

78. How do you safely replace a model that millions of users depend on?
  1. Offline gates: beats the current model on a recent holdout and on key slices; passes latency, size, fairness and calibration checks.
  2. Shadow mode: runs on live traffic, predictions logged but not used; compare with the champion and check for skew and latency.
  3. Canary: 1–5% of traffic with automatic rollback on guardrail breaches.
  4. A/B test for business impact at sufficient power.
  5. Gradual ramp to 100%, keeping the old model warm for instant rollback.

Throughout: version model + data + code together, and monitor service health, inputs, outputs and outcomes.

79. Latency of your model service doubled after a new version was deployed. How do you investigate?

Compare the two versions stage by stage: feature fetching, preprocessing, inference, post-processing, network. Candidates: a bigger model (more trees, deeper, more features); a new feature that needs a slow lookup or an extra service call; preprocessing moved into Python loops; lost batching or caching; a different runtime, thread settings or hardware; cold starts or memory pressure causing swapping; larger payloads. Check p50 vs p99 — if only the tail grew, look at a dependency or garbage collection. Roll back if the SLO is breached, reproduce with a load test, profile, and add a latency budget check to the release pipeline.

80. Your recommender's own suggestions determine what users click, and those clicks become training data. What's the risk and the fix?

A feedback loop. The model only gets feedback on items it chose to show, so popular items collect more clicks, are recommended more, and the rest never get a chance; the model's view of the world narrows and offline metrics computed on its own logs look better than reality. Fixes: reserve a small share of traffic for exploration (random or bandit-based) to get unbiased data; log the probability with which each item was shown and use inverse-propensity weighting in training and evaluation; correct for position bias; monitor diversity, coverage and new-item exposure; and evaluate with online experiments, not only logged data.

81. A loan model can only observe repayment for applicants who were approved. Why is that a problem?

Selection bias: the training data contain no outcomes for the people the previous policy rejected, so the model learns “who defaults among those we already liked” and can be badly wrong for the rejected region — exactly where a new policy might want to expand. Remedies: reject inference techniques (with caution — they rely on assumptions); approve a small random sample of would-be rejects to obtain unbiased labels (the gold standard, at a controlled cost); use bureau or external outcome data for rejected applicants; and at least evaluate and monitor separately near the old decision boundary.

82. How would you decide how often to retrain a model?

Measure the decay instead of guessing: backtest by training at several past dates and scoring each model on later months — the curve of performance against model age shows how fast it goes stale. Combine with the cost of staleness (lost revenue per point of accuracy) and the cost of retraining (compute, validation, risk). Fast-moving domains (fraud, ads, recommendations) need daily or weekly retraining; slow ones (credit risk) quarterly. Add triggers on drift or performance alerts for the unexpected, respect label delay when choosing the training window, and automate the pipeline with validation gates so frequency is cheap and safe.

I · Applied scenarios: forecasting, text, recommendations (83–90)

83. Your demand forecast is consistently too low during festival weeks. How do you fix it?

The model doesn't know the festival is coming. Add calendar and event features: holiday flags, days until/since the festival, festival-specific effects, and — because festivals such as Diwali move in the calendar — align by event date rather than by week number. Include promotion and price features. Make sure the training window contains several past occurrences, and weight or model them explicitly since they're rare. If the model is tree-based, remember it can't predict levels above anything seen; forecast uplift relative to a baseline instead. Also check whether past sales were capped by stock-outs — the history then understates true demand.

84. You need to forecast sales for a product that launched last week. There's no history. What do you do?

Cold start: borrow strength from elsewhere. Use the launch curves of similar past products (same category, price band, brand, season) as a prior — average them or find nearest neighbours on product attributes. A global model trained across all products with attribute features (not just each product's own lags) can predict for a new one. Add signals available before or just after launch: pre-orders, page views, search volume, marketing spend. Give wide prediction intervals, update quickly as each day's sales arrive (Bayesian or simply re-forecasting daily), and tell planners how uncertain it is.

85. Your gradient-boosting forecast flat-lines at the top for a fast-growing product. Why?

Tree models predict averages of training targets within leaves, so they can never output a value larger than what they saw: with a rising trend, future values lie outside the training range and the forecast saturates. Fixes: remove the trend first and model what's left — predict the change (difference) or growth rate, or the ratio to a recent rolling mean, then convert back; or fit a simple linear/exponential trend and let the trees model the residuals; or use a model that extrapolates (linear, ETS, ARIMA, Prophet) for the trend component. Validate specifically on the most recent, highest-level period.

86. A sentiment classifier trained on product reviews performs badly on tweets. Why, and what are your options?

Domain shift: tweets are short, informal, full of slang, emojis, hashtags and sarcasm; the vocabulary and the way sentiment is expressed differ from long, structured reviews, so the features the model relies on are missing or mean something else. Options, cheapest first: label a few hundred tweets and evaluate properly; fine-tune the model on in-domain labelled tweets (even a small set helps a lot with a pretrained language model); continue pretraining on unlabelled tweets; adapt preprocessing (emojis, elongated words, handles); combine both domains in training with a domain indicator. Then monitor — language on social media drifts quickly.

87. Your recommender keeps showing the same popular items to everyone. How do you fix that?

Popularity bias: popular items have the most interactions, so the model learns them best and the feedback loop reinforces it. Remedies: normalise or down-weight popularity in training (e.g. sample negatives by popularity, inverse-propensity weighting); add personalised signals and content features so niche items can be matched; re-rank for diversity and novelty (limit items per category, maximal-marginal-relevance); reserve slots for exploration and new items; and change what you measure — add coverage, diversity and long-term engagement to click-through rate, since CTR alone rewards the safe popular choice. Check by user segment whether heavy and light users both get relevant variety.

88. You must build a classifier but have only 50 positive examples. What's your plan?

With 50 positives, variance is the enemy. Keep the model simple and regularised (logistic regression, small tree ensemble) with a handful of strong, domain-driven features; use repeated stratified cross-validation and report wide confidence intervals; never split positives so thinly that a fold has two or three. Get more signal: transfer learning or pretrained embeddings; weak labels from rules; search for more positives with the first model and have experts verify them (active learning); consider framing it as anomaly detection trained on the plentiful negatives. Be honest that the performance estimate is rough until more positives exist.

89. You clustered customers into five segments. The marketing head asks, “Are these the right segments?” How do you answer?

There's no ground truth, so “right” means stable, distinct and useful. I'd show: stability — do the same segments appear with different seeds, samples and months? Separation — silhouette scores and how different the segment profiles are on the key variables; interpretability — a plain description and name for each (“high-value lapsed”); actionability — would each get a different treatment, and is each big enough to matter? Then validate on behaviour not used in the clustering, and ultimately with a test: do targeted campaigns per segment beat a one-size-fits-all campaign? If not, the segmentation isn't right for this purpose.

90. Your anomaly detector produces 5,000 alerts a day and the operations team reviews 100. What do you change?

The alert volume must match the capacity. Rank alerts by anomaly score and expected impact (score × amount at risk) and send only the top 100; set the threshold from capacity rather than a fixed contamination rate. Reduce false alarms: add context features (what's normal for this customer, hour, device); remove known benign patterns with rules; group alerts that belong to the same incident. Use the analysts' decisions as labels to train a supervised model on top of the anomaly score — precision usually jumps. Track precision at 100 and the estimated misses (sample below the threshold occasionally) so recall isn't forgotten.

J · Stakeholders, judgement & trade-offs (91–100)

91. The business asks for a model with “95% accuracy”. How do you respond?

I'd unpack the number before agreeing to it. What decision will the model drive, and what do the two kinds of error cost? Is accuracy even the right measure (with 3% positives, 97% is trivial)? What does the current process achieve — that's the real benchmark? What's the ceiling given label noise and the available data? Then I'd translate the request into a metric tied to value (e.g. “catch 80% of fraud with fewer than 1 false alarm per 50 transactions”), build a baseline quickly to learn what's feasible, and come back with a realistic target, a range of uncertainty and what it would take to do better.

92. Your model disagrees with a senior domain expert about an important case. What do you do?

Treat it as information, not a contest. Look at the case: which features drove the prediction (SHAP/local explanation)? Is the input data correct? Is the case unlike anything in training (out of distribution)? Does the expert know something the model can't see — context that isn't a feature? If the model is wrong, I've found a missing feature or a data gap. If the expert is using a rule of thumb the data contradict, I'd show similar past cases and their outcomes. For high-stakes decisions I'd keep the human in the loop, log disagreements, and review them regularly — they're the cheapest source of model improvement and of trust.

93. You discover the model's error rate is much higher for one demographic group. What are your next steps?

Measure properly first: per-group error rates, false-positive and false-negative rates, calibration and sample sizes with confidence intervals. Find the cause: under-representation in training data, poorer data quality for that group, label bias from historical decisions, or features that work as proxies. Mitigate: collect or re-weight data; fix features; consider fairness-aware training or group-aware thresholds where that's lawful and appropriate; add human review for affected cases. Escalate to product/legal/compliance — which fairness criterion to satisfy is a policy decision with trade-offs, not something I should settle alone. Then add the group metrics to routine monitoring and document everything.

94. How do you explain to a non-technical executive why the model declined a particular customer?

Start with the decision and the two or three main reasons in plain language: “Declined mainly because of three missed payments in the last six months and credit use above 90%; a long relationship with us counted in their favour.” These come from the model's per-prediction explanation (coefficients or SHAP), translated out of feature names. Add what would change the outcome (“with utilisation below 50%, the application would pass”), how reliable the model is for customers like this one, and the safeguard (appeal/human review). No algorithm names or statistics unless asked — and I'd be clear that these are the model's reasons, not proof of cause.

95. You have two weeks to deliver a churn model. What do you prioritise and what do you skip?

Prioritise: a precise definition of churn and of the prediction moment (days 1–2); a leak-free training set with point-in-time features; a time-based validation that mirrors use; a simple baseline, then one strong model (gradient boosting) with sensible defaults; a metric tied to the retention team's capacity (lift in the top decile); a short error analysis; and a hand-off the business can use — scored list plus top reasons per customer.

Skip for now: exotic models, exhaustive tuning, stacking, real-time serving, elaborate feature stores. I'd state the limitations and a follow-up plan: A/B test of the retention campaign, monitoring, and uplift modelling later.

96. Your model improves the target metric, but customer complaints go up. What happened?

The metric being optimised is a proxy, and the model found a way to raise it that hurts something not measured — clickbait raises click-through, aggressive fraud blocking lowers fraud losses but declines good customers, a retention model pesters people. This is why launches need guardrail metrics (complaints, refunds, unsubscribe rate, latency, long-term retention) alongside the primary metric. I'd quantify the trade-off, look at which users and which predictions drive the complaints, and then change the objective or add constraints: include the cost of false positives in the threshold, cap contact frequency, or optimise a longer-term outcome.

97. A stakeholder asks you to just “use AI” on a problem. How do you decide whether ML is appropriate at all?

I'd check five things. Is there a clear decision that a prediction would improve, and is the value worth the effort? Is there a learnable pattern and enough relevant, labelled data (or a way to get it)? Could simple rules, a lookup or basic analytics solve it well enough? Can the organisation tolerate errors, and act on probabilistic outputs? Can it be maintained — pipelines, monitoring, retraining, ownership? If a heuristic gets most of the benefit, I'd ship that first and use it as the baseline. Saying “this doesn't need ML yet” is a perfectly good — and senior — answer.

98. You find a serious bug in a model that has been live for three months. What do you do?

Contain, then communicate, then learn. Assess the blast radius quickly: which predictions were affected, since when, with what consequence for customers and money. Mitigate at once — roll back, patch, or switch to a fallback. Tell stakeholders promptly and plainly: what happened, the impact, what's been done, what's next; don't wait for a perfect analysis. Decide with the business whether past decisions need correcting (re-scoring, customer remediation, regulatory notification). Then a blameless post-mortem: root cause, why tests and monitoring missed it, and concrete preventive actions — a test that reproduces the bug, a new monitor, a review step.

99. How do you estimate the business value of a model before building it?

Build a back-of-envelope value model. Start from the decision it changes and volumes: for example, 1,000,000 transactions a month, 0.2% fraud at ₹5,000 average loss = ₹1 crore of fraud. If the current rules catch 50% and a model could plausibly catch 65%, that's ₹15 lakh a month gained, minus the cost of extra false alarms (review time, customer friction) and of building and running the system. Give a range (pessimistic/expected/optimistic), name the assumptions that matter most, and propose the cheapest experiment to test them — a quick offline prototype against historical data — before committing a team.

100. Tell me about a time a model you built failed. (How should you structure the answer?)

Interviewers are checking ownership and learning, not perfection. Use STAR with the weight on the last two parts:

  1. Situation/Task: the model, its purpose, and what “failed” meant in numbers.
  2. Action: how you detected it, how you diagnosed it (what you ruled out, what the root cause was — leakage, drift, skew, wrong metric), and what you did in the short term.
  3. Result: the measurable outcome after the fix.
  4. Lesson: what you changed permanently — a validation scheme that mirrors production, a monitor, a pre-launch checklist.

Pick a real technical failure, own your part without blaming others, and avoid “failures” that are disguised successes.
