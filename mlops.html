MLOps & production ML

Modern DS and MLE interviews always ask how a model reaches and survives production: the ML lifecycle, versioning data/code/models, experiment tracking and model registries, feature stores, serving patterns, CI/CD/CT, deployment strategies, and — asked in almost every screen — monitoring, drift detection and retraining.

🎯 Say this in the interview

“MLOps applies DevOps practices to ML, but an ML system has three things that change — code, data and the model — so we version all three, track experiments (MLflow, W&B), register models with lineage, and automate training pipelines. Features are computed once and shared offline/online (a feature store) to avoid training–serving skew. I choose batch, online or streaming serving based on latency needs, release with shadow/canary deployments and A/B tests, and monitor four layers: service health, data quality, drift in inputs and predictions, and model performance once labels arrive. Drift or performance alerts trigger investigation and scheduled or triggered retraining, with automated validation gates and easy rollback.”

The ML lifecycle

Problem framing → data collection & validation → feature engineering → training & experiment tracking → evaluation & validation gates → packaging & registry → deployment → monitoring → feedback & retraining → (back to data). Only a small fraction of a real ML system is model code; the rest is data pipelines, configuration, serving infrastructure, monitoring and process (“Hidden Technical Debt in ML Systems”).

Versioning, experiment tracking & registry

  • Code: Git. Data: DVC, lakeFS, Delta Lake/Iceberg time travel, dataset snapshots with hashes. Environment: pinned requirements, Docker images.
  • Experiment tracking (MLflow, Weights & Biases, Neptune): parameters, metrics, artifacts, code version, data version for every run → compare and reproduce.
  • Model registry (MLflow Model Registry, SageMaker, Vertex AI): versioned models with stages/aliases (staging → production → archived), lineage (which data/code/run produced it), approvals, model cards.
  • Packaging: pickle/joblib (Python-only, version-sensitive), ONNX (portable, fast runtime), MLflow pyfunc, TorchScript, PMML; containerise with Docker.

Feature stores and training–serving skew

  • Training–serving skew: features computed differently in the offline training pipeline (SQL/Spark) and the online service (Java/Python), or data arrives differently — the model sees a different distribution in production.
  • Feature store (Feast, Tecton, Databricks/Vertex/SageMaker feature stores): one definition of each feature, an offline store for training with point-in-time correct joins (no future leakage), an online store (low-latency key-value) for serving, plus sharing, lineage and monitoring.
  • Other mitigations: reuse the same transformation code (sklearn Pipeline inside the model artifact), log features at serving time and train on the logs.

CI / CD / CT for ML

  • CI: unit tests for feature code, data schema & quality tests (Great Expectations, Pandera, TFDV), training-pipeline smoke tests on a sample, linting, reproducibility checks.
  • Model validation gates: new model must beat the current one on a fixed holdout and on key slices, pass fairness/robustness/latency/size checks, and calibration thresholds — otherwise the pipeline stops.
  • CD: automatically package, register and deploy (to staging → canary → prod) with rollback.
  • CT: pipelines (Airflow, Kubeflow, Vertex/SageMaker Pipelines, Prefect, Dagster) retrain on schedule or triggers.
  • Infrastructure as code (Terraform), containers, Kubernetes; secrets & access control; audit logs.

Drift can be sudden (policy change), gradual, incremental or recurring/seasonal. Not all drift hurts the model — confirm impact before retraining.

∑ Population Stability Index
$$\text{PSI}=\sum_{b}(A_b-E_b)\ln\frac{A_b}{E_b}$$

E = expected (training/reference) share in bin b, A = actual (production) share. Rule of thumb: < 0.1 stable, 0.1–0.25 moderate shift, > 0.25 significant. KS statistic = max distance between the two CDFs (sensitive at large n — p-values become tiny for trivial shifts, so use effect-size thresholds).

Retraining strategies

  • Scheduled (daily/weekly/monthly) — simple, predictable; may be wasteful or too slow.
  • Triggered by drift or performance alerts — efficient, needs reliable monitors.
  • Online/incremental learning — continuous updates (SGD, partial_fit, river) for fast-changing data; risk of instability and poisoning.
  • Choose the training window: sliding window (forget old regimes) vs expanding (more data); weight recent data more.
  • Always run validation gates + shadow/canary before promoting; keep the previous version for rollback.
  • Beware feedback loops: the model's decisions change future training data (e.g., only approved loans get repayment labels) — use exploration, holdout groups, reject inference.

Incident playbook: “accuracy dropped from 92% to 78%”

  1. Is it real? Check the monitoring pipeline, label delays, metric computation, sample size.
  2. When did it start? Correlate with deployments, upstream data changes, product launches, seasonality.
  3. Data quality: schema changes, null spikes, new categories, unit changes, broken joins, stale features.
  4. Drift analysis: which features shifted (PSI per feature), prediction distribution, segment-level performance.
  5. Training–serving skew: compare logged online features vs offline recomputation for the same entities.
  6. Mitigate: roll back, fall back to rules/previous model, fix pipeline; retrain on recent data if concept drift.
  7. Post-mortem: add the missing monitor/test, document, adjust retraining policy.

Interview questions

What is MLOps and why is it needed?

The set of practices to reliably build, deploy, monitor and improve ML systems in production — combining ML, data engineering and DevOps. It's needed because models depend on changing data, fail silently, must be reproducible and auditable, and need retraining; without automation, models rot and releases are slow and risky.

What is the difference between data drift and concept drift?

Data (covariate) drift: the distribution of inputs P(X) changes (e.g. a new customer demographic). Concept drift: the relationship between inputs and target P(Y|X) changes (e.g. fraudsters adapt, so the same features now mean something else). Data drift is detectable without labels; concept drift usually needs labels or proxy signals.

How do you detect drift in production?

Compare production windows against a reference (training or a stable period): per-feature statistics and tests (PSI, KS, χ², Jensen–Shannon/Wasserstein), prediction-distribution monitoring, multivariate detectors (domain classifier: train a model to distinguish reference vs production — AUC ≫ 0.5 means drift), data-quality checks, and performance metrics once labels arrive. Alert on effect-size thresholds, not just p-values.

What should you monitor for a deployed model?

Service health (latency percentiles, errors, throughput, resources), data quality (schema, nulls, ranges, new categories, freshness, volume), input and prediction drift, model performance on labelled feedback (overall and by segment), business KPIs, fairness metrics, and cost.

What is training–serving skew and how do you prevent it?

A mismatch between the data/features the model saw in training and what it receives in production — different code paths, data sources, timing or preprocessing. Prevent with a feature store (shared definitions, point-in-time correct offline data), packaging preprocessing inside the model artifact, logging serving features and training on them, and skew monitors comparing online vs offline features.

Batch vs real-time inference — how do you choose?

Batch when predictions can be precomputed and a delay is acceptable (daily churn scores) — cheaper and simpler. Real-time when the decision depends on fresh context at request time (fraud at checkout, search ranking) — needs low-latency serving, online features and higher operational cost. Streaming in between for continuous event-driven scoring.

Explain shadow, canary and blue–green deployments.

Shadow: new model gets a copy of live traffic but its predictions aren't used — safe validation. Canary: a small share of real traffic goes to the new model, ramped up if metrics hold. Blue–green: two full environments; traffic switches from blue (old) to green (new) at once, enabling instant rollback.

What is a feature store?

A centralised system for defining, computing, storing and serving features: an offline store (historical values with point-in-time joins for training) and an online store (low-latency latest values for inference), with metadata, sharing/reuse across teams, lineage and monitoring. Examples: Feast, Tecton, Databricks, Vertex AI, SageMaker Feature Store.

What does a model registry provide?

Versioned storage of model artifacts with metadata (metrics, parameters, training data and code versions), lifecycle stages/aliases (staging, production, archived), approval workflows, lineage, and a single source of truth that deployment pipelines pull from — enabling reproducibility, audits and rollbacks.

How do you decide when to retrain a model?

Based on how fast the domain changes and the cost of staleness vs retraining: scheduled retraining matched to the drift rate, triggered retraining on drift/performance alerts, or online learning for fast-moving data. Use backtests to estimate how performance decays with model age, and always gate new models with validation and canaries.

How do you ensure reproducibility of ML experiments?

Version code (Git), data (snapshots/DVC/hashes) and environment (pinned dependencies, Docker); fix random seeds; log parameters, metrics and artifacts with experiment tracking; parameterise pipelines with configs; record lineage in the model registry.

Your model's accuracy dropped suddenly in production. Walk through your investigation.

Verify the alert (label delay, metric bug). Find the start time and correlate with deployments and upstream changes. Check data quality (schema, nulls, units, broken joins, stale features). Measure feature and prediction drift and per-segment performance. Compare online vs offline features for skew. Mitigate (rollback/fallback/fix pipeline), retrain if concept drift, then add monitors/tests and write a post-mortem.

What tests would you put in an ML CI pipeline?

Unit tests for feature transformations; data validation (schema, ranges, null rates, distribution expectations); training smoke test on a small sample; model quality gates vs the current champion on a fixed holdout and critical slices; invariance/directional tests (e.g. increasing income shouldn't increase default risk); latency and artifact-size checks; fairness checks; API contract tests.

How would you handle delayed ground-truth labels when monitoring?

Monitor leading indicators: input drift, prediction-distribution drift, data quality, business proxies (e.g. early repayment signals). Estimate performance with calibrated confidence (CBPE). Build pipelines that join labels when they arrive and backfill performance dashboards; set retraining cadence around label availability.

What are feedback loops in ML systems and how do you mitigate them?

When predictions influence the data the model is later trained on — recommendations shape clicks; credit models only observe outcomes for approved applicants; predictive policing. They bias training data and can amplify errors. Mitigate with exploration (randomised holdouts, bandits), logging propensities and using inverse-propensity weighting, reject inference, and monitoring diversity/coverage.

How would you serve a model with very tight latency (e.g. < 10 ms)?

Precompute heavy features and cache them in an online store; use a lightweight model or distil/quantise a big one; export to an optimised runtime (ONNX Runtime, Treelite for trees); keep the model in memory in a compiled service; batch where possible; colocate with callers; autoscale; set timeouts with a fallback (default score or rules).
